# Reward Proofs

A reward proof is a cryptographic artifact generated by Aether's oracle signer that enables
a user or tenant system to claim a reward from a tenant-owned smart contract. Aether generates
the proof; the tenant or user submits the claim.

## Proof Lifecycle

```
created → used (on-chain claim submitted)
        → revoked (manually revoked by operator)
        → expired (expiry timestamp passed without use)
```

Proofs can only transition from `created` to one terminal state. Used and revoked proofs
cannot be reused.

## Proof Format (EVM Production)

Current production format is EIP-191 personal_sign. An EIP-712 typed data format is
available in the backend signer and is the preferred format for new contract deployments.

### EIP-191 Proof Fields

```json
{
  "proof_format": "eip191",
  "wallet_address": "0x...",
  "action_type": "conversion",
  "amount": "1000000000000000000",
  "nonce": "<32-byte hex>",
  "expiry": 1750000000,
  "chain_id": 1,
  "contract_address": "0x...",
  "message_hash": "0x...",
  "signature": "0x...",
  "signer_address": "0x..."
}
```

### EIP-712 Proof Fields (preferred for new contracts)

```json
{
  "proof_format": "eip712",
  "wallet_address": "0x...",
  "campaign_id": "<bytes32>",
  "rule_id": "<bytes32>",
  "decision_id": "<uuid>",
  "action_type": "conversion",
  "amount": "1000000000000000000",
  "nonce": "<bytes32>",
  "expiry": 1750000000,
  "chain_id": 1,
  "contract_address": "0x...",
  "message_hash": "0x...",
  "signature": "0x...",
  "signer_address": "0x...",
  "domain": {
    "name": "AetherRewardEnabler",
    "version": "1",
    "chainId": 1,
    "verifyingContract": "0x...",
    "tenantId": "tenant_...",
    "campaignId": "<bytes32>"
  }
}
```

## Replay Prevention

- Each proof has a unique `nonce` (32-byte random value).
- The smart contract tracks `usedNonces` as a mapping.
- A proof with a used nonce is rejected on-chain with `NonceAlreadyUsed`.
- Aether tracks proof status in `reward_proofs.status`; a proof in `used` or `revoked`
  state cannot be regenerated with the same `decision_id`.
- Proof expiry (`expires_at`) enforced both in Aether (blocks delivery of expired proofs)
  and on-chain (`block.timestamp > expiry` → `ClaimExpired`).

## Proof Expiry

Default: `REWARD_PROOF_EXPIRY_SECONDS=3600` (1 hour). Configurable per environment.

Expired proofs:
- Are not returned via `GET /v1/rewards/proofs/{id}` (returns 410 Gone).
- Cannot be used to claim on-chain (contract rejects).
- A new proof can be generated for the same decision if the proof expired and the
  campaign is still active and the user is still eligible.

## Tenant Contract Registry

To generate a proof, the target contract must be registered in `tenant_contract_registry`.

Required fields per registration:

```json
{
  "tenant_id": "tenant_...",
  "chain_id": 1,
  "contract_address": "0x...",
  "contract_name": "MyRewardContract",
  "abi_ref": "s3://tenant-contracts/MyRewardContract.abi.json",
  "verification_status": "verified",
  "allowed_campaign_ids": ["cmp_..."],
  "oracle_signer_address": "0x..."
}
```

- `verification_status` must be `verified` before proofs can be generated.
- `oracle_signer_address` must match the Aether oracle signer address for the tenant's key ref.
- A proof can only target an `allowed_campaign_ids` entry.
- `REWARD_CONTRACT_REGISTRY_REQUIRED=true` (default in production) blocks proof generation
  if no registry entry exists.

## Signer Key Management

Reward proof signer keys are **tenant-scoped credentials** resolved through the
durable credential authority — never a deployment-global environment variable.
`services/rewards/signing.py::resolve_reward_signer(tenant_id, environment,
chain_family)` is the only sanctioned path:

- Production/staging: the tenant's `reward_signer` provider slot
  (`evm_reward_signer_key` / `svm_reward_signer_key`) for the credential
  environment (`sandbox` | `live`), stored KMS-encrypted, versioned, rotatable,
  and revocable. The slot's `key_derivation_check` validation derives the public
  identity (secp256k1 address / ed25519 verify key) to prove the material is a
  usable signing key before activation.
- Local/test only: `ORACLE_SIGNER_KEY` (or the Hardhat dev key) as a
  credential-free bootstrap. **There is no environment-variable fallback
  outside local/test** — a tenant with no ACTIVE `reward_signer` credential
  gets `SignerUnavailableError` (fail-closed) and the capability stays at
  `credential_waiting`. The retired global `ORACLE_SIGNER_KEY` no longer signs
  any tenant's proofs in a deployed environment, and the module no longer reads
  a signer key at import time.
- Contract-registry verification (`POST /v1/rewards/contracts/{id}/verify`)
  compares `oracle_signer_address` against the tenant's **resolved** signer
  (fail-closed: verification never passes if `eth_account` is unavailable or the
  signer cannot be resolved).
- Credential rotation demotes bound capabilities to `credential_supplied`
  (re-certification required); revocation demotes to `revoked` — propagated to
  the capability lifecycle authority automatically.
- On the smart contract side, oracle rotation uses `rotateOracle(oldOracle, newOracle)` to
  keep the on-chain oracle address in sync.

## Non-EVM Chains (Beta)

| Chain | VM Type | Status | Notes |
|---|---|---|---|
| Ethereum, Polygon, Avalanche, etc. | EVM | Production | EIP-191/EIP-712 |
| Solana | SVM | Beta | Ed25519 signing; proof format defined |
| Bitcoin | BITCOIN | Beta | Inscription-based; proof format defined |
| Sui | MOVEVM | Beta | Ed25519 signing; proof format defined |
| NEAR | NEAR | Beta | Ed25519 signing; proof format defined |
| TRON | TVM | Beta | EVM-compatible; proof format defined |
| Cosmos | COSMOS | Beta | Amino signing; proof format defined |

Beta chains: proof format is defined in `services/oracle/multichain_signer.py` but
production signing has not been verified against live networks. Do not use for real rewards.

## Proof Revocation

Proofs can be revoked by a tenant operator via `POST /v1/rewards/proofs/{id}/revoke`.
Revocation is audit-logged. A revoked proof:
- Cannot be delivered to the tenant dApp.
- Cannot be regenerated with the same `decision_id` unless the tenant explicitly creates
  a new evaluation with a new idempotency key.
- Does not affect the on-chain contract state (only Aether's proof record is updated).
  If the proof was already submitted on-chain before revocation, the revocation has no effect.
