# Provider Capability Matrix Guide

The canonical, machine-readable capability matrix is generated, not authored:

- **Data:** `docs/_generated/adapter-certification-matrix.json` (never edit by
  hand — regenerated by `scripts/docs_extract/extract_adapter_certification.py`
  via `make extract-docs`; CI fails on drift).
- **Report / gate:** `make credentialless-certification` (report, exit 0) and
  `make credentialless-certification-strict` (fails if any first-release
  provider is below `CREDENTIAL_WAITING` or is `SCAFFOLDED`).
- **Operator narrative:**
  `docs/productization/economic-interoperability-intelligence/ADAPTER_CAPABILITY_MATRIX.md`.

## How the matrix is built

Each adapter publishes an `AdapterCertificationDescriptor` (its supported
operations, required credentials/endpoints, pagination/streaming model, and its
`CredentialReadiness` state). `build_capability_matrix()` in
`shared/certification/registry.py` resolves every provider's state **from
source** on every call — no hand-typed states, byte-stable output.

## Reading a provider entry

Keys are `<domain>:<provider>`. Each entry carries `state`, `state_rank`,
`capabilities`, `required_credentials`, `required_endpoints`, `secret_ref_names`,
`pagination_model`, and `streaming_model`.

### Readiness states (low → high)

| State | Rank | Meaning |
|---|---|---|
| `mocked_local` | 0 | deterministic local mock, no real transport |
| `scaffolded` | 1 | descriptor only, unimplemented paths (forbidden for first release) |
| `credential_waiting` | 2 | code-complete + infra-defined, credential-gated, NOT yet validated |
| `replay_validated` | 3 | validated against recorded fixtures |
| `sandbox_validated` | 4 | validated against a provider sandbox |
| `partner_live` | 5 | validated against a live provider |
| `degraded` / `disabled` | −1 / −2 | off-ramp: regressed or pulled (ranked below all) |

`degraded`/`disabled` rank below everything so an "at least CREDENTIAL_WAITING"
assertion never admits an off-ramped provider.

## Current first-release scope (all `credential_waiting`)

18 providers, none live: derivatives (drift, dydx, gmx, hyperliquid), interop
(axelar, chainlink_ccip, debridge, hyperlane, ibc, layerzero, wormhole),
payments (bridge, coinbase, moonpay, privy, stripe_onramp), stablecoin_chain
(evm, svm). `credential_waiting` is **not** production-ready — see
`CREDENTIAL_WAITING_PROMOTION_GUIDE.md`.

> Field caveat: for derivatives, `capabilities` come from the live adapter but
> `streaming_model`/`pagination_model` come from a fixed spec table, so dydx can
> advertise `realtime_account_stream` while reporting `streaming_model: none`.
> Trust the capability list for what an adapter can observe; the model fields
> describe the currently-wired transport.
