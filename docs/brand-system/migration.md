# Brand-system migration playbook

Use this checklist for a focused route or component migration. Do not combine a
visual migration with a backend, authorization, or data-contract rewrite.

## 1. Classify what changes

| You are changing | Use | Preserve |
| --- | --- | --- |
| Product header, favicon, lockup | Identity manifest plus `BrandMark`/product lockup | Approved asset geometry, parent/product relationship, accessible name. |
| Navigation or action glyph | Navigation/action taxonomy plus `NavigationIcon`/`Icon` | Route, label, capability/permission gate, direct-url behavior. |
| Connector, payment rail, social/channel source | Provider registry plus provider renderer | Runtime provider ID, visibility/entitlement, connection/health state. |
| Person, org, wallet, graph node | Entity taxonomy plus entity renderer | Entity type, graph data, source overlay, profile behavior. |
| Live/gated/failed/stale state | Existing capability truth plus status renderer | State labels, descriptions, data attributes, remediation. |
| Urgency, evidence, time/source | Severity/confidence/freshness/provenance renderer | The distinction between those concepts and their labels. |
| Card, dialog, overlay or transition | Surface, focus, token and motion metadata | Reduced-motion behavior and visible focus. |

## 2. Apply the smallest correct API

```tsx
// Named route icon. `decorative` is valid because the nav label is visible.
<NavigationIcon destination="kyber-connectors" decorative size="md" />

// Meaningful provider identity with a visible label generated by the chip.
<ProviderSourceChip provider={connector.connector_type} />

// A provider label can be decorative only when a label is already adjacent.
<ProviderMark provider={providerId} decorative size={20} />

// Separate operational truth from source identity.
<StatusIcon status="sandbox_validated" />
<SeverityIcon severity="high" />
```

Do not use status color as a provider treatment. Do not map `sandbox_validated`
to `live`, or turn an unavailable/credential-gated provider into a healthy
marketing card.

## 3. Add a missing registry value

1. Confirm the contract/source ID and whether it is actually eligible to
   render. A brand registry entry cannot grant visibility.
2. Add the taxonomy entry with a stable identifier, visible label, description,
   and aliases only where aliases are presentation-safe.
3. Add a focused source-of-truth test. For a provider, assert alias resolution
   retains the requested ID and unknown input returns the neutral fallback.
4. Use the shared renderer in the smallest consumer. Add a component/route test
   that asserts the semantic identity and preserves the prior behavioral gate.
5. Check compact/narrow behavior, keyboard focus, and text alternatives.

## 4. Acceptance checklist

- [ ] No SVG paths, remote logo URL, provider color table, ASCII nav glyph, or
      new base palette was added to the feature.
- [ ] Existing route paths, labels, capability/permission checks, auth and
      backend behavior are unchanged.
- [ ] Meaningful icons have an accessible name; decorative icons have adjacent
      text and are hidden from assistive technology.
- [ ] Provider identity remains separate from health, severity, entitlement,
      confidence, freshness, provenance, and remediation.
- [ ] Focus is visible, touch targets are appropriate, and reduced motion
      preserves loading/error/state text.
- [ ] Targeted tests pass. Final integration runs `make docs-fix` and then
      `make ci-check`; hosted checks remain a separate delivery condition.

## 5. Transitional exceptions

Compatibility components may remain temporarily only as delegates to
`@aether/ui`; they must not retain independent SVG geometry, provider paths, or
icon mappings. A neutral provider fallback is allowed indefinitely until a
local reviewed mark is approved. Generated documents and test fixtures are not
production asset sources and must never be edited to paper over a registry gap.
