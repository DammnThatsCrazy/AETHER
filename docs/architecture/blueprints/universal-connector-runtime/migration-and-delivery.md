# Universal Connector Runtime: migration and delivery

**Blueprint status, 2026-10-03:** migration plan with an in-branch foundation. The branch adds durable route records, generation checks and an opt-in guarded graph-write seam, but does not activate tenant traffic cutover or establish that every legacy writer uses the guard. No new live certification or production readiness is claimed. The term *Universal Connector Runtime* describes shared behavior built by extending the existing **Universal Provider Runtime (UPR)** in `services/api/connectors/provider_runtime/`; it is not a second deployable runtime. Commerce is the first domain pack to prove the common behavior, not a separate ingestion plane.

This plan is subordinate to the existing [provider migration](../../../operations/PROVIDER-MIGRATION.md), [provider certification](../../../reference/PROVIDER-CERTIFICATION.md), [provider plugin specification](../../PROVIDER-PLUGIN-SPEC.md), [commerce event contract](../../../reference/COMMERCE-EVENT-CONTRACT.md), and [connector runtime target](../../target/connector-runtime-productization.md). The implementation squad must reconcile those authored documents when behavior changes. The target page is updated in this blueprint branch to distinguish the existing native Shopify orders plugin and legacy Shopify/Stripe connectors from the proposed full runtime; future implementation must keep that inventory current rather than create a second catalog.

The existing Bronze and consent systems remain authoritative. The blueprint must keep `RawProviderRecord` and `AetherEvent` compatibility, the provider registry, existing credential service, ManagedIntegration, tenant-scoped graph authority, and the repo's documentation ownership map. The branch adds raw schema-v2 source revisions, source-object identity helpers, and an `AetherEvent` v2 logical/interpretation ID core while preserving v1 serialization and dedupe behavior. The `provider_object_refs` mapping remains repository-only: Shopify normalizers and emitted events do not use its IDs, and graph projection does not consume it. The durable logical-fact ledger, cross-version migration map, source authority/reconciliation, and graph projection remain target work; do not silently replace IDs or bypass the established identity resolver.

**Current pre-enable gate:** provider raw admission resolves `source_id="provider-account:{connection_id}:{account_id}"` and requires a tenant-scoped grant matching the verified connection, provider identity as `connector_id`, `connector_class="tenant_byod_data"`, and explicit tenant-lake permission. An admitted raw record references an immutable tenant-scoped `RightsDecision`; replay verifies that original decision and makes a fresh rights check. The canonical `DataRightsService` persists grants and create/revoke lifecycle events through the migration-owned repository. Staging/production admission and replay remain fail-closed if PostgreSQL or the required schema is unavailable; omitted use permissions default to false. Existing quarantined rows from the earlier path lack persisted admission evidence and an original allowed decision reference; current replay rejects them, and no historical-row re-admission path exists. Any future path must resolve immutable decision evidence for the unchanged raw row and pass a fresh rights check. Bronze raw/source/provenance/quarantine fields reject post-insert mutation except that `BronzeRepository.update` may append IDs to `payload.metadata.confirmed_signal_ids`. Quarantine does not grant indefinite audit retention: raw data can be retained only under the current rights and retention basis and remains subject to deletion/suppression. Treat the database/schema readiness check and evidence-backed admission as prerequisites before provider promotion, not a flag or manifest setting.

## 2. Invariants and control records

1. **One production writer.** For each `(tenant_id, integration_id, provider_identity, account_id, stream_id, canonical_fact_family)`, exactly one route may submit graph-affecting events. A shadow route may write only to an isolated comparison store. A "dual write" mode, if retained for compatibility with prior plans, means legacy production output plus new isolated shadow output; it never means two production graph writers. Enforce this in the shared graph mutation/admission seam, not just a UI flag.
2. **Raw before canonical.** Verify source/connection scope and resolve raw rights before durable retention of signed, pulled, or imported payload. Keep the raw record with its decision reference only while the approved retention basis remains valid; then normalize. A normalization failure becomes a typed quarantine outcome only when the raw record is eligible for retention, not a fabricated event or an audit-retention exception. The existing UPR raw-store and bridge ordering are the starting point.
3. **Stable lineage.** Preserve provider object ID, legacy event ID, original occurrence time, source payload version, connection/account, and consent decision. Map old IDs to canonical IDs through durable, tenant-scoped aliases. Replays retain the same business identity and normalizer version evidence.
4. **Authority is field-specific.** Order/catalog authority, payment/payout authority, ad spend authority, communication delivery authority, and SDK observation authority differ. Transport deduplication alone cannot settle semantic duplicates. `managed_integrations/source_authority.py` can inform precedence but its stated boundary is not downstream economic or identity truth.
5. **Fail closed on missing evidence.** Unknown credential status, absent webhook verification, ambiguous identity, missing authority rule, missing diff window, or missing rollback evidence blocks promotion. A tenant's `connected` label is not provider certification or graph readiness.
6. **Tenant and operator boundaries.** Tenant routes derive tenant identity from server auth context; Kyber controls require operator authorization, reason, change/evidence ID, and audit record. Credentials remain references, never plaintext in cutover records, API responses, diff artifacts, logs, or fixtures.

Implement a durable `TenantConnectorRoute` (name illustrative; final schema follows the shared contract review) with a unique key for the tuple above, `mode`, `writer_generation`, `revision`, source and target connection refs, manifest/normalizer/contract versions, shadow namespace, decision actor/reason, effective time, rollback deadline, and last evidence bundle ID. Use compare-and-swap on revision and generation fencing at every graph enqueue. An old worker with a stale generation must fail closed after the route switches. Store transitions and prior values in an append-only audit ledger. Do not overload `ProviderConnection.state`: connection lifecycle and tenant traffic authority are different axes.

Allowed route modes are `legacy_only`, `shadow`, `new_primary`, and `legacy_disabled`. `shadow` keeps legacy as the single production writer and routes the new output to isolated storage. `new_primary` changes the single writer to UPR while keeping legacy connection/credentials available for a bounded rollback window. `legacy_disabled` is permitted only after the rollback window and decommission gates. A requested `dual_write` label maps to `shadow` until isolated-store semantics and writer fencing are verified.

## 3. Migration phases and exit gates

### M0 — inventory and baseline

Create a machine-readable migration map per provider capability, account, stream, and tenant integration. Enumerate legacy `BaseConnector` registrations, native plugins, comms/measurement/derivatives connectors, webhook routes, SDK `/v1/batch`, import/Data Exchange paths, raw and normalized stores, identity aliases, graph consumers, projections, consent policy, readiness UI, credentials, cursors, and in-flight jobs. For each path record `keep`, `wrap`, `migrate`, `defer`, or `retire_after_cutover`, its owner, contracts, current environment availability, and evidence. Use the generated adapter certification matrix as a reference, not a new handwritten readiness score.

**Exit:** every production-reachable path has an owner and routing classification; active tenant integrations have counts, freshness, money totals by currency, lifecycle states, identity-link counts, graph/projection checksums, quarantine/error rates, webhook lag, and current cursor captured for a bounded baseline window. Missing baselines are explicit blockers.

### M1 — compatibility and contract convergence

Extend `LegacyConnectorPlugin` and the existing UPR normalization/bridge seams to produce canonical contracts without changing the legacy writer. Preserve legacy namespaced event types for existing consumers until versioned consumers accept their canonical counterpart. Add deterministic canonical-ID alias mapping and reversible lineage from legacy records. Reconcile dotted `commerce.*` events with the SDK event registry through the dedicated contract process noted in `docs/reference/COMMERCE-EVENT-CONTRACT.md`; do not hand-edit generated unions. Define source-authority rules and equivalence keys for each field and duplicate scenario before any graph promotion.

**Exit:** fixtures for same record through old and new adapters give deterministic, schema-valid output; missing/ambiguous mappings quarantine; provider raw evidence and consent behavior are preserved; no new graph route is enabled. Contract migrations include forward/backward consumers and a tested downgrade/rollback strategy.

### M2 — isolated shadow and canonical diff

Mirror authenticated ingress **after** provider signature/tenant binding or reuse the same verified raw record. Do not send two provider API pulls when a single captured page can feed both normalizers. Keep shadow raw, canonical, authority decisions, proposed graph mutations, and projection results in a separate namespace with retention and PII policy. Block shadow bus topics from production graph subscribers and verify that isolation in tests. Persist a `CanonicalDiffRun` with tenant, provider capability, account/stream, time window, legacy/new versions, input watermark, sample size, exclusions, thresholds, result, and evidence artifact references.

Compare stable semantic keys and lifecycle, not only event counts: source and canonical IDs/aliases; missing and extra orders, products, customers, refunds and fulfillments; money in integer minor units and currency; time ordering; identity linkage; authority outcomes; proposed graph node/edge changes; lens totals; freshness; quarantine; consent rejections. A result must distinguish schema difference, expected intentional mapping change, late-arriving data, and defect. Keep diffs tenant-scoped and redact PII/secrets from operator summaries.

**Exit:** at least one complete initial-sync window and one incremental/webhook window have reproducible diffs; every critical difference is resolved or explicitly approved with a versioned mapping rule. Zero duplicate production graph mutations is a hard gate. Refund/payment amount, currency, tenant ownership, consent, and graph identity mismatches have **zero tolerance** unless a documented, reviewed semantic change explains them. Other numeric thresholds must be named in the provider certification policy before a run; a global "match rate" alone cannot pass.

### M3 — provider and sandbox certification

Run existing `certify_provider` for each **capability**, then add end-to-end fixture, sandbox, and tenant-readiness evidence outside that offline harness. A passing offline `CertificationReport` does not upgrade manifest readiness. Validate OAuth/credential lifecycle, required scopes, account selection, initial and incremental sync, cursor resume, signed webhook delivery/dedupe, rate-limit/retry, normalization and quarantine, replay, source authority and reconciliation, graph/projection, consent, tenant isolation, UI status, and alerts. The Shopify reference currently covers `orders_read`; other object/financial capabilities require distinct manifests/adapters or an explicit documented scope exclusion.

The first provider vertical-slice acceptance target is the [commerce reference slice](commerce-reference-slice.md): prove Shopify store/order facts, an independent payment/refund source, and SDK observation/correlation through one source-authority and graph/projection path. Its specific scenario and evidence gate precede expansion to additional providers; it does not promote Shopify to a whole-commerce or live-certified claim by itself.

**Exit:** `replay_validated` evidence covers offline determinism; `sandbox_validated` requires real provider sandbox and staging evidence; `partner_live` requires live credentialed evidence and operations approval under the existing readiness rules. Keep external activation blockers separate from code completion. No manifest environment bit is raised merely to make a test pass.

### M4 — controlled tenant cutover

Advance one tenant integration at a time: internal tenant, test/demo tenant, design partner, then new and existing tenants in reviewed cohorts. The ManagedIntegration rollout record may track rings and health, but a separate audited apply operation must change the durable route and writer generation. Before each switch, take a cursor/watermark snapshot, identify in-flight jobs and webhook inbox deliveries, run the cutover checklist below, then atomically promote one writer. Drain or reject stale-generation work, replay the bounded handoff interval idempotently, compare post-switch outputs, and keep the legacy path intact until the rollback deadline.

**Exit per tenant:** one authoritative writer proven by data-plane telemetry; no critical canonical diff; required data freshness and graph/lens checks pass; readiness is truthful; rollback is rehearsed; run ID, actor, policy version, evidence links, cursor snapshot, and old/new generation are recorded. Promotion stops automatically when an invariant fails. A cohort does not advance from a percentage or green UI badge alone.

### M5 — bounded backfill and reprojection

Use a durable job with tenant/provider/account/stream and closed time bounds, dry-run counts, normalizer/contract versions, cost and rate-limit budget, cursor checkpoint, lease, retries, idempotency key, cancellation, and audit receipt. Start with 7 days, then 30, then 90, then full history only if required and reviewed. Raw provider replay, provider API backfill, canonical renormalization, graph restatement, projection replay, attribution recomputation, and readiness recalculation are separate job types with explicit dependencies. Original occurrence time and source IDs survive every run. A backfill must not consume SDK replay's in-memory run journal as durable provider progress.

**Exit:** provider and graph counts/monetary totals reconcile for each completed window, no duplicate facts or cross-tenant aliases appear, and every gap is quarantined or explained. Record the cost, rate-limit, watermarks, replay versions, and projection checksums in the evidence bundle.

### M6 — rollback and stabilization

Triggers include duplicate graph writes, missing orders/refunds, currency or net-value mismatch, identity merge regression, bad webhook verification/lag, consent regression, repeated quarantine, cursor gap, false readiness, tenant-visible lens regression, and unavailable rollback evidence. An operator or automatic hard gate pauses the cohort, fences the current writer generation, returns the affected tenant integration to the last safe route, restores its cursor/watermark, and replays only the handoff gap. The cutover state transition does not itself delete Bronze artifacts, aliases, or diff evidence; retention, deletion, and suppression still follow their governing rights and lifecycle decisions. Mark new artifacts as shadow/ignored/superseded for downstream authority as appropriate, then reconcile projections against the source records that remain authorized for retention.

**Exit:** the legacy or previous writer is active exactly once; stale new workers cannot publish graph mutations; freshness catches up; product and financial projections match pre-switch plus legitimately new events; incident and fix evidence are attached. If the old credential, schema, or provider API no longer works, pause ingestion and surface degraded readiness rather than claim a successful rollback.

### M7 — provider-by-provider decommission

Retire a legacy provider capability only after all active tenant integrations have passed M4/M5, rollback windows expire, provider certification remains current, no legacy traffic or queued work remains, replay and support runbooks are tested, and owned docs/tests/UI paths are reconciled. Replace the existing process-local, provider-wide Shopify retirement marker with a durable, restart-safe decommission decision consumed by all workers before treating it as operational authority. Remove old routes/workers only after callers have been inventoried and compatibility windows close. Produce a decommission report with tenants, traffic zero-proof, retained raw data and aliases, contract versions, incident history, and restoration path.

**Exit:** no active tenant depends on the old path; disabling/removing it survives process restarts; old webhook addresses have a documented redirect or rejection window; no consumer expects legacy event types; generated and authored docs reflect the actual shipped behavior.

## 6. Tenant promotion checklist and evidence bundle

A `CutoverEvidenceBundle` should contain: immutable decision ID; tenant/integration/provider/account/stream; route generation before/after; actor and approval; versions of plugin, manifest, contract, normalizer, source-authority rules, graph projection; baseline and shadow time windows; input watermarks and cursors; certification reports; signed-webhook and credential health; consent and tenant-isolation results; diff report with critical mismatches and explicit dispositions; reconciliation of counts and monetary totals by currency; quarantine/freshness/lag; product surface checks; replay rehearsal; rollback deadline and expected previous route; and monitoring links. Store artifact refs with access control and retention, not raw PII in the bundle.

The promotion controller rejects if any required field is absent, the evidence is stale for its configured window, a manifest is unavailable in the target environment, a provider's live evidence is only an offline test, the old or new route is not uniquely identified, a previous cutover is unfinished, or approvals/tenant policy are unsatisfied. The evidence reviewer signs a specific bundle revision; changing thresholds, mapping, or code invalidates that approval. Risk classes and approvals should reuse `managed_integrations` policy rather than an ad hoc bypass.

Suggested initial hard gates: zero cross-tenant access, zero unverified webhook accepted, zero duplicate graph fact keys, zero unexplained financial/refund mismatch, zero unreviewed ID collision, and zero missing required source authority. Product-specific freshness and volume tolerances must be set from an observed baseline and written into the provider policy before evaluation. Low-volume windows need fixture/sandbox evidence rather than a misleading 100% match from empty traffic.

## 7. Operational runbooks to ship with code

| Runbook | Operator steps and durable evidence |
|---|---|
| Start shadow | Verify tenant/provider/account scope, capture baseline and watermark, create isolated namespace, fence graph output, start mirrored feed, verify no shadow event reaches production graph; record route generation and run ID. |
| Investigate diff | Freeze comparison window; inspect signed raw lineage, normalizer/contract versions, excluded late events, authority and identity decisions, money by currency, graph proposal; classify expected/defect/quarantine; rerun same inputs deterministically. |
| Promote tenant | Check the signed evidence bundle and approvals; compare-and-swap one durable route; drain stale workers; replay handoff interval; verify post-switch graph/lens and tenant readiness; record rollback deadline and monitor. |
| Roll back tenant | Pause cohort; snapshot current cursor; fence new generation; switch to previous approved writer; replay gap once; diff and restate projection; leave still-authorized raw records and audit evidence intact; apply any independent retention/deletion/suppression decision; publish incident and degraded state until checks recover. |
| Backfill/replay | Preview records/cost/limits; choose bounded time range and versions; authorize; run durable checkpointed job; monitor quarantine and spend; resume/cancel safely; compare source and projection totals; retain receipt. |
| Rotate/revoke credential | Use credential broker and tenant scoped refs; retest scopes and webhook secret, stop unsafe sync, mark degraded readiness, resume from saved cursor only after verification; never paste secrets into runbook artifacts. |
| Decommission | Confirm zero tenants/traffic/queued work and expired rollback windows; persist decommission state; restart workers and verify; remove/redirect legacy routes in a later reviewed slice; archive evidence and restoration procedure. |

Alerts should cover webhook verification failures, raw-to-canonical lag, sync cursor stalls, high quarantine, money/refund mismatch, identity collision, shadow isolation violation, stale writer generation, duplicate graph attempt, readiness contradiction, and missing rollback path. Triage views must separate provider outage, Aether code failure, credential/permission failure, and external activation waiting.

## 8. Risks and deliberate sequence

The riskiest change is a data-plane switch that lets both legacy and UPR publish graph facts. WP2 and WP3 therefore precede any live cohort. A credential projection alone does not prove native sync can use the projected credential; the Shopify mapping warns that its migrated credential may need manual completion. The existing provider reconciliation engine checks raw-store counts only when a plugin supplies a reconciliation adapter, which Shopify currently does not. Whole-commerce financial reconciliation belongs in WP4. The SDK replay runner handles only SDK Bronze rows and cannot substitute for provider backfill. Process-local legacy retirement cannot be used for durable migration state.

Other risks are provider API schema drift, webhook retries during the writer flip, alias collision after reconnect, currency/rounding defects, historical refund restatement, provider rate/cost limits, false readiness from a successful connection test, and PII leaking into diff reports. Each has a corresponding fixture, hard gate, quarantine path, or runbook above. Provider expansion waits until shared routing and authority are exercised by Shopify and one non-commerce source; this proves the runtime is modular across domains.

## 9. Verification and repository delivery cadence

Follow root `AGENTS.md` and `docs/reference/source-of-truth/repo_consistency_ownership.json`. During implementation keep the PR **draft** and run only affected local tests, type/lint checks, contract parity, fixture replay, migration validation, docs checks, and focused UI tests. Use the project Python interpreter (`.venv/bin/python` where available) and select commands from the affected packages. Record exact commands and failures in the PR evidence. Do not repeatedly run `make verification-disposition`, `make ci-check`, `make release-gate`, or dispatch hosted PR CI for each work package.

At integration, the chief reviews architecture and clarification gaps, ownership-required docs and contracts, and each source-linked page against its `source_files`; updates authored content; runs `make docs-generate` for generated/sync-managed surfaces when their inputs changed; then runs `make docs-generate-changed` **only** for reviewed stale source-linked pages. Run focused checks and `make docs-verify-idempotent`; keep generated, synced, source-hash, migration, package/version and contract artifacts in the same reviewable change. Mark the draft PR ready for review only after that work is complete. The `ready_for_review` event starts the single normal PR authority in `.github/workflows/repo-consistency.yml`, with terminal `verification / disposition`. A failed authority may rerun after a material fix. `make ci-check` is separate broad/trusted-main/nightly or explicitly requested evidence; `make release-gate` and `scripts/production_status.py` are needed for release claims, not for ordinary blueprint progress.

### Completion definitions

- **Provider capability done:** honest manifest and adapters, raw and canonical fixture coverage, tenant-bound auth/webhook/sync, authority and quarantine behavior, replay, graph/projection proof, current certification evidence for the enabled environment, and a support runbook.
- **Tenant integration done:** durable `new_primary` route and writer-generation proof, zero critical diff, truthful readiness, bounded replay and rehearsed rollback, evidence bundle and monitoring. `legacy_disabled` is a later state after stabilization.
