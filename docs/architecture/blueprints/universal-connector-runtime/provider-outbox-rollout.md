# Provider canonical outbox rollout

## Current code and required deployment state

The provider pull scheduler and verified webhook gateway resolve raw-data rights before retaining a provider payload. The rights source is `provider-account:{connection_id}:{account_id}`; the grant must be tenant-scoped to the verified connection, use that provider identity as `connector_id`, set `connector_class=tenant_byod_data`, and grant tenant-lake permission. A permitted admission carries an immutable tenant-scoped `RightsDecision` reference. The canonical `DataRightsService` now persists grants and create/revoke events through the migration-owned tenant-scoped repository. Staging/production admission remains fail-closed when the database or required migration schema is unavailable; omitted use permissions default to false. No raw payload or webhook request body is retained when the rights check fails. After successful admission, Bronze provenance must still be `valid` and quarantine status `not_quarantined` before normalization. Historical provider rows created before this admission gate may remain quarantined and cannot reach `EventBridge`, canonical `bronze_sdk_events`, `event_outbox`, or the relay. `EventBridge` then applies the existing ingress scrub and consent decision, and uses `ingestion.bronze_bulk.ingest_many` to commit an accepted `AetherEvent` to typed `bronze_sdk_events` and `event_outbox` in one transaction. Duplicate `(tenant_id, event_id, schema_version)` keys do not enqueue another outbox row. A failed transaction leaves neither canonical Bronze nor outbox row, so the caller fails instead of advancing its cursor or acknowledging its webhook inbox as processed. The existing `event_outbox_relay` publishes pending events at least once to `SDK_EVENTS_VALIDATED`; consumers must remain idempotent.

`AETHER_PROVIDER_RUNTIME_ENABLED` is the real ingress switch: it mounts authenticated sync and verified webhook routes. `AETHER_PROVIDER_SYNC_SCHEDULER_ENABLED` additionally starts background pull, but is not required for webhook or manual sync ingress. In staging and production, API and split worker startup now fail closed if provider runtime ingress is enabled while `OUTBOX_RELAY_ENABLED` is false. Local/dev/integration log a warning so focused tests can drain manually. This guard proves configuration coherence only; it cannot prove that a separate relay task is healthy.

## Deployment order and health evidence

1. Apply the existing `bronze_sdk_events`/`event_outbox` schema and hash-chain migrations. Start the `outbox-relay` runtime role and set `OUTBOX_RELAY_ENABLED=true`; retain its readiness endpoint (`/ready` or `/readyz`) as an independent release check. Keep the `stream-worker` and `identity-worker` roles healthy for the validated topic consumers.
2. Verify the relay is claiming and publishing a safe test event, and that `event_outbox` pending/retry depth and oldest `available_at` are bounded. Monitor `ingestion_outbox_relay_claimed_total`, `ingestion_outbox_relay_published_total`, `ingestion_outbox_relay_retried_total`, and `ingestion_outbox_relay_dead_lettered_total`. A rising dead-letter count or claims without publishes stops rollout. Use the worker readiness evaluator and broker subscription health; the environment flag alone is not delivery evidence.
3. Keep `AETHER_PROVIDER_RUNTIME_ENABLED` off in staging/production until `DataRightsService` reads grants from durable tenant-scoped storage and tests prove the provider-account grant check admits permitted records while missing, denied, expired, or uncertain grants fail closed before raw-body retention. Default Bronze provider records from the earlier path are quarantined, and raw replay rejects them. Enabling a durable grant store does not by itself admit historical rows: replay must validate their immutable referenced `RightsDecision` and make a fresh rights check. After both prerequisites pass, enable one internal connection, then permit one signed webhook and one bounded pull page. Confirm the rights decision and raw row exist before normalization, the canonical Bronze row and outbox row share tenant/event identity, relay publishes once in the normal case, and duplicate input does not enqueue a second job. Compare downstream analytics and Silver outputs with source authority rules before expanding tenants.
4. Keep the connector route in legacy or isolated shadow mode until tenant-specific canonical diff, writer fencing, and rollback evidence pass. A queued outbox event is not permission to mutate a production graph. Route generation and downstream graph/Silver admission remain separate work; do not promote a tenant on the basis of this outbox slice alone.

## Failure and replay operations

| Symptom | Evidence to capture | Safe response |
|---|---|---|
| Relay disabled or absent | Release startup failure, role inventory, relay `/ready`, pending outbox age | Start or restore the existing `outbox-relay` role and confirm readiness before enabling provider ingress. Pending rows remain durable. |
| Broker publish failure | Outbox status `retry`, attempt count, last error, relay retry metric | Restore broker/credential health. The relay retries with a lease and backoff. A crash after publish and before mark may redeliver; verify consumer idempotence. |
| Dead-lettered row | Tenant/event/topic, attempt count, redacted error, original Bronze/raw references | Quarantine the affected scope, fix the cause, then use a reviewed, tenant-scoped requeue or replay procedure. No automatic provider dead-letter requeue is implemented here. |
| Raw rights admission denial | Generic public webhook denial or failed sync outcome, bounded tenantless reason metric for pre-auth webhook rejection, unchanged cursor; no retained Bronze payload or webhook request body | Correct or durably provision the account grant, then retry the provider acquisition through the checked path. Staging/production remain fail-closed unless the migrated grant and lifecycle-event schema is available. Do not persist denied raw content as an audit exception. The public denial does not expose the internal reason label or tenant/account IDs. |
| Canonical persistence or historical raw admission failure | Existing quarantined Bronze row, missing/corrupt rights-decision reference, pull run/webhook inbox failure, missing canonical Bronze/outbox pair | Raw Bronze source/payload/provenance/quarantine fields are immutable after insert; `BronzeRepository.update` allows only appending IDs to `payload.metadata.confirmed_signal_ids`. Pre-gate rows lack persisted admission evidence and an original allowed `RightsDecision`, so current replay rejects them and no historical-row re-admission path exists. Any future re-admission requires immutable referenced decision evidence for the unchanged Bronze row plus a fresh current rights check. Never manually clear quarantine/provenance fields. Retain or delete raw only under its active rights and retention basis; quarantine is not an audit-retention exception. |
| Historical bridge publish gap | Legacy `bronze_connector_events` row, tenant, source record, canonical event id, destination dedupe state | Revalidate consent and current retention policy; replay through the current normalizer and bridge in a bounded tenant/account/stream window. Diff outputs before admitting production writes. |

The old bridge wrote canonical events to `bronze_connector_events` and published in process. The bounded `provider.raw_replay` job described below reads only the persisted `bronze_provider_records` raw envelope; it does not copy historical `bronze_connector_events` rows or repair missing historical raw records. Any migration must inventory the old table, preserve only raw lineage whose current rights and retention basis allow it, avoid replaying erased subjects, use the current consent/privacy gate, and compare event IDs and source revisions before tenant cutover. Never copy old payloads directly into `event_outbox` or requeue a dead-lettered event without a reviewed tenant scope and current policy decision.

## Bounded raw replay job

`provider_runtime.replay.ProviderRawReplayService.enqueue` is an internal service seam that creates a `provider.raw_replay` job on the existing durable jobs platform. It requires a nonblank run key, operator reference, and reviewed decision reference, plus an explicit immutable scope: tenant, connection, provider identity, selected account, stream, closed Bronze ingestion time window, record cap (at most 10,000), dry-run choice, pinned normalizer version, and pinned canonical event schema version. The service checks the installed normalizer and current connection/account association before enqueue and again before execution. In staging and production it refuses to enqueue without a database. The handler is registered in both API and dedicated worker processes when `AETHER_PROVIDER_RUNTIME_ENABLED` is on, and is not tenant-invocable through `POST /v1/jobs`.

The reader keyset-scans `bronze_provider_records` by `(created_at, id)` with database-side tenant, provider, connection, account, stream, and time predicates. It checks each selected row's raw checksum and Bronze dedup/lineage fields before normalization. A result that changes the pinned normalizer version, event schema, tenant, provider, account, or source-record lineage fails the job. A dry run re-evaluates current consent and acquisition scrub on transient normalized events and persists only its job checkpoint/result; it does not write canonical Bronze, outbox, graph, or connector routes. A live run re-evaluates current consent through `EventBridge`, which commits accepted canonical Bronze and outbox together. The job checkpoints the raw cursor after each record using a lease-owner condition. A crash after the bridge commits but before the checkpoint can reprocess that record; stable event IDs and canonical Bronze/outbox uniqueness make the retry idempotent. The job reports `scanned`, normalized `candidates`, newly `accepted` events, explicit normalizer `skipped` records, and dry-run policy admissions. `candidates - accepted` must **not** be interpreted as duplicates: it can also include consent denials.

Every replay row must have `provenance_status=valid`, `quarantine_status=not_quarantined`, and a reference to its original immutable, tenant-scoped, allowed `RightsDecision`. The decision's source must be `provider-account:{connection_id}:{account_id}` and must match a tenant-scoped grant whose `connector_id` is the provider identity, `connector_class` is `tenant_byod_data`, and tenant-lake permission is granted. Replay verifies the original decision and performs a fresh rights check against current grant state before normalization; a stale or missing decision, revoked/expired/missing grant, tenant mismatch, or denial blocks replay. `DataRightsService` currently keeps grants in process memory, so staging/production cannot safely admit or replay provider raw until the grant store is durable. Existing quarantined rows from the earlier path lack persisted admission evidence and an original decision reference, so they remain blocked; no historical-row re-admission path exists. A future path must resolve immutable decision evidence for the unchanged row and perform a fresh current rights check. Bronze source and payload evidence is immutable after insertion except that `BronzeRepository.update` may append IDs to `payload.metadata.confirmed_signal_ids`. Quarantine does not authorize indefinite audit retention; the current rights and retention decision governs preservation, deletion, and suppression.

For an internal reviewed run, first confirm the connection/account still belongs to the tenant, the referenced `RightsDecision` belongs to the same tenant and provider-account source, a fresh rights check allows the requested use, the selected normalizer version is deployed, the raw table and jobs table are durable, and the outbox relay is healthy. Enqueue a narrow dry run, inspect its job result and any integrity failure, then enqueue a distinct live run only after checking policy and expected event IDs. Monitor the job timeline and outbox lag; a `partially_succeeded` result with `limit_reached` means the cap stopped the scan and the persisted cursor is evidence for a separately reviewed continuation. A failed job retains its last committed cursor; the jobs platform retry resumes from it. Do not widen a window or replay a failed/dead-lettered scope automatically. This job never advances pull cursors, acknowledges webhook inboxes, changes a tenant route, or bypasses graph writer admission.

There is no public replay route or authoritative operator RBAC/approval verification at this seam: `actor_ref` and `decision_ref` are required audit references, not proof of authorization. A Kyber/admin API must enforce RBAC and record the reviewed decision before invoking it. There is also no automatic legacy-table migration, erased-subject exclusion ledger, or paginated backfill planner. Historical v1 raw records without `stream_id` are intentionally outside this strict reader. Before using replay for tenant cutover, add those policy and backfill controls, compare graph/Silver projections separately, and retain route-generation fencing.

## Consumer and authority boundary

`SDK_EVENTS_VALIDATED` is the existing observation fan-out topic. The relay source marker makes `sdk_bronze_writer` skip a duplicate Bronze write. A backend-origin provider guard now defers `silver_normalizer`, `silver_fact_projector`, `analytics_event_recorder`, identity signal emission, and real-time identity resolution for provider `AetherEvent` payloads. It accepts the historical direct bridge source service without the new `source_type` marker, and requires the marker for shared outbox/replay source services. Each defer increments `ingestion_provider_projection_deferred_total` with only the low-cardinality consumer name; this is visible unfinished work, not a successful provider projection. The source service is assigned by the backend producer and is adequate to prevent an SDK request body from opting out by adding a marker, but the shared topic has no cryptographic producer attestation. A stronger origin boundary or a dedicated provider topic remains a hardening option before production cutover.

The semantic consumer also subscribes to the topic and still applies its own eligibility/quarantine policy. `to_observation_view` understands the `AetherEvent` shape when the normalization-spine flag is enabled, but some flat SDK reads remain when it is off. The Silver dispatcher has no `commerce.order.*` projector in this slice. Provider payment/order authority therefore still requires explicit source-authority, provider-aware projectors, tenant route fencing, and tests across both flag states. Do not infer confirmed order/payment truth from an SDK observation or an outbox publish.
